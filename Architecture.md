# Debt Tracker - Архитектура приложения

## 1. Обзор проекта

Я разрабатываю веб-приложение для личного использования, которое буду хостить на домашнем мини ПК. Цель приложения: трекинг должников и переплат по клиентам (люди, ФОП, предприятия), которым я выставляю счета.

Ключевая логика: на главном экране я вижу список клиентов с текущим статусом баланса по каждому (должен мне / я должен ему / оплачено полностью). Кликнув на клиента, я попадаю на его страницу, где веду историю выставленных счетов и оплат.

Приложение однопользовательское (только я как администратор), доступ закрыт логином и паролем.

## 2. Технологический стек

- **Фреймворк**: Next.js 14+ (App Router), фронтенд и бэкенд в одном приложении
- **База данных**: SQLite (один файл, легко бэкапить, не нужен отдельный сервер БД)
- **ORM**: Prisma
- **Стилизация**: Tailwind CSS
- **Аутентификация**: NextAuth.js (credentials provider) или собственная реализация на сессионных cookie с хешированием пароля через bcrypt
- **Интернационализация**: next-intl или next-i18next (русский и английский)
- **Деплой**: Docker-контейнер, запуск через docker-compose на мини ПК, доступ через локальную сеть или обратный прокси (Caddy/Nginx) с HTTPS, если планируется доступ извне

Если у меня уже есть предпочтения по стеку, отличные от указанных (например, я работаю с MongoDB в других проектах), это единственный пункт, который стоит пересмотреть перед началом разработки. Для такого маленького объема данных SQLite проще в администрировании, чем поднимать MongoDB отдельным сервисом.

## 3. Модель данных

### Client (Клиент)
| Поле | Тип | Описание |
|---|---|---|
| id | UUID | Первичный ключ |
| name | String | Имя / название (человек, ФОП, предприятие) |
| type | Enum | person / kindergarten / school |
| contactInfo | String? | Телефон, email (опционально) |
| notes | Text? | Заметки |
| createdAt | DateTime | Дата создания записи |
| archived | Boolean | Скрыт ли клиент из основного списка |

### Invoice (Выставленный счет)
| Поле | Тип | Описание |
|---|---|---|
| id | UUID | Первичный ключ |
| clientId | UUID | Ссылка на клиента |
| date | Date | Дата выставления счета |
| amountMinor | Int | Сумма счета в минимальных единицах валюты (копейки/центы), не Decimal |
| description | String? | За что выставлен счет |
| createdAt | DateTime | Дата создания записи |

### Payment (Оплата)
| Поле | Тип | Описание |
|---|---|---|
| id | UUID | Первичный ключ |
| clientId | UUID | Ссылка на клиента |
| date | Date | Дата оплаты |
| amountMinor | Int | Сумма оплаты в минимальных единицах валюты (копейки/центы), не Decimal |
| description | String? | Комментарий к оплате |
| createdAt | DateTime | Дата создания записи |

**Почему не Decimal.** SQLite не имеет нативного типа Decimal, Prisma эмулирует его через NUMERIC, и при `SUM()` по множеству строк есть риск накопления ошибки округления. Для денежного трекера, где вся ценность в точности баланса, храню суммы как целые числа в минимальных единицах валюты (копейки для грн, центы для доллара), а в интерфейсе делю на 100 только при отображении. Это исключает саму возможность ошибки округления, потому что SUM по Int в SQLite точен всегда.

### Settings (Настройки)
Так как приложение однопользовательское, это одна строка в таблице, а не отдельная сущность на пользователя.

| Поле | Тип | Описание |
|---|---|---|
| id | UUID | Первичный ключ (всегда одна запись) |
| theme | Enum | light / dark |
| currencySymbol | String | Символ валюты по умолчанию (например, грн, $, €) |
| language | Enum | ru / en |
| updatedAt | DateTime | Дата последнего изменения |

Тема и язык дополнительно дублируются в cookie/localStorage на клиенте, чтобы интерфейс применял их мгновенно при загрузке страницы, до ответа от сервера. При расхождении побеждает значение из БД: как только приходит ответ от `/api/settings`, клиент перезаписывает локальное значение серверным, даже если оно отличается от того, что уже отрисовано. БД, а не cookie, это источник истины, локальное значение существует только для мгновенного первого рендера, а не как равноправная копия.

### Важное правило
Баланс клиента никогда не хранится как отдельное поле в базе. Он всегда вычисляется на лету:

```
balance = SUM(invoices.amountMinor) - SUM(payments.amountMinor)
```

Результат в минимальных единицах, деление на 100 происходит только на этапе отображения, не при расчете и не при хранении.

- balance > 0: клиент должен мне (эта сумма)
- balance < 0: я должен клиенту (переплата)
- balance == 0: оплачено полностью

Это исключает ситуацию, когда где-то в коде забыли пересчитать сохраненную сумму после добавления новой записи.

## 4. Структура страниц

### 4.1 Главная страница (Home)
- Список всех клиентов в виде карточек или таблицы
- Перед именем каждого клиента: цветной индикатор и сумма
  - Красный: "Должен мне: 1500 грн"
  - Зеленый: "Переплата: 200 грн" (я должен клиенту)
  - Серый/нейтральный: "Оплачено полностью"
- Поиск и фильтр по имени
- Сортировка: по сумме долга, по алфавиту, по дате последней активности
- Кнопка "Добавить клиента"
- Переключатель языка (RU/EN) в шапке

### 4.2 Страница клиента
- Имя, тип, контактные данные (редактируемые)
- Крупный блок с текущим балансом
- Две колонки или таблица с историей: счета и оплаты (можно объединить в единую ленту, отсортированную по дате, с пометкой типа записи)
- Форма быстрого добавления счета: дата, сумма, описание
- Форма быстрого добавления оплаты: дата, сумма, описание
- Возможность редактировать и удалять отдельные записи
- Кнопка архивации клиента

### 4.3 Страница настроек
- Переключатель темы: светлая / темная (сохраняется между сессиями)
- Выбор валюты по умолчанию (символ, применяется ко всем суммам в интерфейсе)
- Выбор языка интерфейса (RU/EN), дублирует переключатель из шапки
- Смена пароля от аккаунта

### 4.4 Страница логина
- Поле логин/пароль
- Защита от брутфорса: ограничение попыток входа

### 4.5 Страница отчета по обороту
- Выбор периода: дата начала и дата окончания (произвольный диапазон, не только месяц)
- Опциональный фильтр по конкретному клиенту, по умолчанию отчет по всем клиентам
- Сводка за период: баланс клиента на начало периода, сумма всех выставленных счетов за период, сумма всех полученных оплат за период, чистое изменение (счета минус оплаты), баланс на конец периода (равен балансу на начало плюс чистое изменение)
- Таблица с разбивкой по каждому клиенту: те же пять чисел на каждого
- Кнопка экспорта в CSV и в Excel (xlsx)

## 5. API endpoints

```
POST   /api/auth/login
POST   /api/auth/logout

GET    /api/clients              - список клиентов с вычисленным балансом
                                    query-параметры:
                                    ?search=строка       - поиск по имени (частичное совпадение, регистронезависимое)
                                    ?sortBy=balance|name|lastActivity  - поле сортировки
                                    ?order=asc|desc      - направление сортировки
                                    ?includeArchived=true - включить архивных клиентов в список
                                    по умолчанию: sortBy=lastActivity, order=desc, includeArchived=false
                                    (архивные клиенты по умолчанию не показываются на главной, но их
                                    данные остаются доступны через этот параметр или напрямую по /api/clients/:id)
                                    lastActivity = MAX(date) среди всех invoices и payments клиента;
                                    если у клиента нет ни одной записи, используется createdAt клиента
                                    (такой клиент считается наименее активным при сортировке по убыванию)
POST   /api/clients              - создать клиента
GET    /api/clients/:id          - данные клиента + история
PATCH  /api/clients/:id          - редактировать клиента
DELETE /api/clients/:id          - soft-delete: устанавливает archived=true, реальная запись из БД
                                    не удаляется, история счетов и оплат сохраняется; возвращает 204

POST   /api/clients/:id/invoices - добавить счет
PATCH  /api/invoices/:id         - редактировать счет
DELETE /api/invoices/:id         - hard-delete: строка реально удаляется из БД (это исправление
                                    ошибки ввода, а не архивная операция)

POST   /api/clients/:id/payments - добавить оплату
PATCH  /api/payments/:id         - редактировать оплату
DELETE /api/payments/:id         - hard-delete: строка реально удаляется из БД (это исправление
                                    ошибки ввода, а не архивная операция)

GET    /api/settings             - получить текущие настройки
PATCH  /api/settings             - обновить тему / валюту / язык
POST   /api/auth/change-password - сменить пароль

GET    /api/reports/turnover     - отчет по обороту за период
                                    query-параметры:
                                    ?from=YYYY-MM-DD     - начало периода (обязательный)
                                    ?to=YYYY-MM-DD       - конец периода (обязательный)
                                    ?clientId=UUID       - фильтр по клиенту (опционально)
                                    архивные клиенты (archived=true) всегда включены в отчет,
                                    includeArchived здесь не применяется: архивация скрывает
                                    клиента только с главного экрана, но не из финансовой истории
                                    возвращает: balanceAtStart, totalInvoiced, totalPaid,
                                    netChange, balanceAtEnd, и массив по клиентам с теми же
                                    пятью полями на каждого
                                    сводные (top-level) поля считаются по всем invoices/payments
                                    в базе за период (или отфильтрованным по clientId, если указан)
                                    каждая строка в массиве по клиентам использует ту же формулу,
                                    но отфильтрованную по своему clientId: то есть balanceAtStart
                                    для строки клиента X это SUM(invoices.amountMinor) минус
                                    SUM(payments.amountMinor) по записям именно клиента X с date < from,
                                    и так же для totalInvoiced, totalPaid, netChange, balanceAtEnd
                                    balanceAtStart = SUM(invoices.amountMinor) - SUM(payments.amountMinor)
                                    по всем записям с date < from
                                    balanceAtEnd = balanceAtStart + netChange
GET    /api/reports/turnover/export?format=csv|xlsx  - выгрузка того же отчета файлом
```

Все эндпоинты, кроме /api/auth/login, требуют активной сессии.

## 6. Требования к UI/UX

- Максимально простой и понятный интерфейс, минимум кликов до основного действия (добавить счет/оплату)
- Мобильная адаптивность, так как я буду заходить в приложение и с телефона
- Цветовая индикация статуса баланса должна считываться с первого взгляда, без необходимости читать текст
- Формы добавления записи должны открываться в модальном окне или инлайн, без перехода на отдельную страницу
- Подтверждение перед удалением записи

## 7. Интернационализация (i18n)

- Все текстовые строки интерфейса вынесены в файлы локализации (ru.json, en.json)
- Формат даты и валюты меняется в зависимости от выбранного языка
- Выбор языка сохраняется в localStorage или в cookie, чтобы не сбрасывался при перезаходе
- Данные клиентов (имена, описания) не переводятся, это пользовательский ввод

## 8. Безопасность

- Обязательная аутентификация для всех страниц, кроме логина
- Пароль хранится в базе только в хешированном виде (bcrypt)
- Сессия через httpOnly cookie с атрибутом SameSite=Strict, этого достаточно для защиты от CSRF на state-changing эндпоинтах (POST/PATCH/DELETE), так как приложение не встраивается в чужие сайты и не принимает кросс-доменные запросы с сессионной cookie
- Если приложение будет доступно из интернета (не только из локальной сети), обязательно HTTPS через обратный прокси
- Rate limiting на эндпоинте логина

## 9. Деплой на мини ПК

- Приложение упаковано в Docker-контейнер
- docker-compose с volume для файла SQLite базы данных, чтобы данные не терялись при пересборке контейнера
- Регулярный автоматический бэкап файла базы данных (например, копия в отдельную папку раз в сутки через cron)
- Порт приложения по умолчанию закрыт для внешнего доступа, доступ только из локальной сети, если явно не настроен обратный прокси с HTTPS

## 10. Подход к разработке: test-first

Я пишу тесты до кода, но не для всего подряд, а по приоритету риска. Порядок такой:

1. **Бизнес-логика расчета баланса.** Это самое критичное место в приложении, ошибка здесь означает неверную сумму долга. Пишу тест на функцию расчета баланса до того, как пишу саму функцию: пустой клиент, только счета без оплат, только оплаты без счетов, переплата, точное совпадение в ноль, несколько счетов и несколько оплат вперемешку по датам, а также сумма большого количества мелких amountMinor (проверка, что SUM по Int в SQLite не теряет ни копейки при агрегации сотен строк).
2. **API эндпоинты изменения данных** (создание/редактирование/удаление счета и оплаты). Тест до реализации: проверяю, что после POST баланс клиента пересчитывается правильно, что DELETE реально убирает запись из агрегации, что нельзя изменить чужую запись без авторизации.
3. **Аутентификация.** Тест до реализации: неверный пароль не пускает, правильный пускает, сессия истекает, эндпоинты без сессии возвращают 401.
4. **Сортировка и поиск в списке клиентов.** Тест до реализации: поиск по частичному совпадению имени, сортировка по балансу в обе стороны, сортировка по дате последней активности (включая случай клиента без единой записи, у него используется createdAt).
5. **Отчет по обороту.** Тест до реализации: клиент без записей до начала периода (balanceAtStart = 0), клиент с историей до периода (balanceAtStart считается корректно по записям со date < from), проверка что balanceAtEnd равен balanceAtStart плюс netChange во всех случаях.

Компоненты интерфейса (кнопки, модальные окна, переключатель темы) я пишу без теста заранее, ошибки там видно сразу визуально, а вложенное время в тест-фёрст для верстки не окупается на проекте такого масштаба.

Инструменты: Vitest для юнит-тестов бизнес-логики, Supertest или встроенный fetch-клиент Next.js для теста API-роутов на реальной тестовой SQLite-базе (не мок, а настоящая база в памяти, чтобы тест агрегации SQL был честным).
